# ReedGuard

ReedGuard is a standalone Uniswap v4 hook for native-ETH/token pools. It collects a fixed 1.0% ETH hook fee, lets its immutable owner pause swaps per pool, and enforces a 30-second cooldown per pool and `tx.origin`. It creates no token, liquidity position or pool.

The launch deploys **only `ReedGuardDeployer`**. Its nonpayable constructor searches salts from zero upward, then creates `ReedGuard` with CREATE2 in the same transaction. `hook()` returns the resulting address. There is no later deploy or initialization function.

## Build and test

All dependencies are ordinary source files under `lib/`; no network, submodule, environment file, FFI or filesystem permission is needed to build or test. Foundry must have Solidity **0.8.26** installed. `foundry.toml` pins that compiler, Cancun, optimizer settings, `via_ir` and `bytecode_hash = "none"`.

```sh
forge build
FOUNDRY_FUZZ_SEED=0x6f3abb40f6e8e0ab01bbac70f5d9de1e1c5158618d84eeb732fd96b25f53612e forge test
forge fmt --check
```

Tests use the vendored real v4 `PoolManager`, local ERC-20 fixtures and a local settlement router. They require no RPC and do not broadcast. The stateful invariant suite mixes swaps, pauses, time advances, recipient rejection and claims across three pools, including two pools with the same token. It checks ETH/token conservation, fee backing and per-pool state isolation. See [the security review](docs/SECURITY.md) and [dependency pins](docs/DEPENDENCIES.md).

## Launch parameters

The following are the parameters supplied by the assignment, not addresses discovered or generated by this project:

| Item | Value |
| --- | --- |
| Chain | Robinhood Chain, chain ID `4663` |
| Application to deploy | `ReedGuardDeployer` |
| Constructor argument 1: `IPoolManager poolManager_` | `0x8366a39CC670B4001A1121B8F6A443A643e40951` |
| Constructor argument 2: `address owner_` | `$owner`, resolving to `0x5Bff2a2FEcD1d6152676813b21346238733bEAB1` |
| Constructor argument 3: `address feeRecipient_` | `0x5Bff2a2FEcD1d6152676813b21346238733bEAB1` |
| Deployment value | `0` |
| Salt argument | None |
| Hook permission bits | `0x20cc` / `8396` |

The deployer passes all three arguments unchanged to `ReedGuard`. Both constructors reject an invalid configuration through the hook's local validation; they make no calls to the manager, owner, fee recipient or token, and do not require those addresses to contain code. The deployer's only contract creation is its hook. The constructor trace test verifies this on an empty local chain.

The CREATE2 preimage uses the **new deployer's address**, the complete hook init code including these arguments, and the salt. The first matching salt is chosen; every lower salt has been considered. `HookDeployed(hook, salt)` records it. There is no off-chain salt parameter or subsequent deployment step. Mining reuses a fixed memory buffer. The search is intentionally unbounded as requested; its gas cost depends on the actual deployer address and init code. The launch operator must simulate the exact factory deployment and provide enough transaction gas for that search. Changing source, compiler options or arguments changes the result.

This repository contains the launchable contracts and tests. It contains no `launch.json`, private key, signing flow, broadcast or assumed final contract address. The launch pipeline supplies the manifest and records the confirmed deployer and `hook()` address.

## Pools and public interface

Anyone may call the supplied PoolManager's `initialize` with `currency0 = address(0)` (native ETH), a nonzero ERC-20 `currency1`, and this hook's address. ERC-20/ERC-20 pools, including WETH/token pools, are rejected. The PoolManager still validates currency ordering, price, tick spacing and LP fee. ReedGuard does not restrict the initializer, token supply, initial price, or otherwise valid LP fee tier. It accepts the 12,500 tier. A dynamic-fee pool retains v4's initial LP fee because this hook exposes no LP-fee updater or override.

`PoolId` is `keccak256(abi.encode(PoolKey))`, including currencies, fee, tick spacing and hook. In ABI calls, it is a `bytes32`. Use the exact pool ID, even when two pools have the same token.

| Function on ReedGuard | Caller / meaning |
| --- | --- |
| `pause(PoolId poolId)` | Owner only; blocks swaps in this initialized pool |
| `unpause(PoolId poolId)` | Owner only; permits swaps, subject to cooldown |
| `paused(PoolId poolId)` | Whether swaps are paused |
| `nextSwapAt(PoolId poolId, address wallet)` | Earliest allowed block timestamp for this origin in this pool |
| `claimFees(PoolId poolId)` | Anyone; redeems available deferred ETH to the fixed recipient; returns amount redeemed |
| `claimableFees(PoolId poolId)` | Outstanding ETH amount in wei attributed to this pool |
| `token(PoolId poolId)` | The initialized pool's `currency1` address |
| `totalSupply(PoolId poolId)` | Calls that token's current `totalSupply()`; no cached or invented supply |
| `poolManager()`, `owner()`, `feeRecipient()` | Immutable deployment configuration |
| `getHookPermissions()` | The fixed callback permissions |

Unknown pool IDs return default zero/false from the mapping views; token/supply lookup, pause, unpause and claim actions reject them. Pause and unpause are idempotent. Neither resets the cooldown. Liquidity additions, removals, zero-liquidity fee collection and donations are unaffected by pause, and none pays a hook fee.

Events are `PoolRegistered`, `Paused`, `Unpaused`, `SwapCooldown`, `FeePaid`, `FeeDeferred`, and `FeesClaimed`. Every pool event includes the pool ID. The hook neither owns nor transfers the user's liquidity position.

## ETH fee accounting and rounding

All percentage calculations use v4 `FullMath.mulDiv`. The fee is `floor(ETH basis * 100 / 10_000)`, in wei, with no minimum fee. The basis and v4 delta handling are:

| Swap mode | Fee basis | Result |
| --- | --- | --- |
| Buy, exact ETH input `S` | Completed input budget `S` | Fee `F` withheld from the budget; pool trades `S - F`; user pays `S` |
| Buy, exact token output | Actual gross ETH input from the pool's `amount0` delta | Fee added to that ETH input; token output untouched |
| Sell, exact token input | Actual gross ETH output from the pool's `amount0` delta | Fee deducted from that ETH output; token input untouched |
| Sell, exact ETH output `S` | Completed requested ETH receipt `S` | Pool produces `S + F`; user receives exactly `S`; recipient gets `F` |

Thus for ETH-specified swaps the fee basis is the completed caller-specified ETH amount; for token-specified swaps it is the pool's realized ETH delta before the hook adjustment. LP/protocol swap fees are separate and remain part of v4's normal accounting. No percentage is applied to token amounts or total supply. No price calculation, oracle, outside pool, token conversion or external pricing service is needed.

ETH-specified swaps return a specified-currency fee delta in `beforeSwap`. In `afterSwap`, the raw ETH delta **must equal `params.amountSpecified + F`**; otherwise `PartialETHFill` reverts the entire swap, including all fee and cooldown state. This prevents charging the promised fee for a partially filled order. Token-specified swaps may fill partially and pay only on the realized ETH delta. A router must respect the returned net deltas, supply appropriate price limits, and enforce its own minimum-output/maximum-input constraints.

Every fee is settled during the paying swap. When the manager has enough native ETH, the hook calls `take` directly to the recipient. When it has too little, or that transfer reverts, the hook mints native-ETH ERC-6909 claims **in the existing PoolManager**, held by the hook on the recipient's behalf. These are not a new token deployed by ReedGuard. The equal positive hook fee delta cancels the take/mint debit; the swapper settles the corresponding ETH charge. The token-side hook delta is always zero.

The hook keeps a separate claim ledger for every pool even though the PoolManager aggregates its ETH claims under currency ID zero. Anyone can redeem one pool's ledger with `claimFees(poolId)`, outside an existing manager unlock. The hook burns only that pool's recorded amount and takes ETH to the same immutable recipient. Claims can be redeemed while paused. The claim caller never receives the proceeds.

A call redeems up to the available manager ETH and the v4 signed-delta limit; any remainder stays attributed to that pool. No claims or no available ETH returns zero. If the recipient rejects redemption, the entire call reverts, preserving the claim ledger and ERC-6909 balance for a later retry. Rejecting recipients therefore do not halt swaps, but must eventually accept ETH to receive their fees. Unsolicited transfers of claims or assets to the hook are not credited to any pool and have no rescue function.

## Cooldown and authority

`COOLDOWN = 30 seconds`. The first successful swap is allowed immediately. Subsequent swaps by that `tx.origin` in the same pool require `block.timestamp >= nextSwapAt(poolId, tx.origin)`. The timer is set before any fee transfer; a reverted swap rolls it back. A successful zero-fill token-specified swap also counts as a swap. Both buys and sells share the timer.

This is a timestamp throttle, not identity verification or sandwich protection. Separate originating wallets can bypass it. Switching to another relayer/origin changes the identity seen by the hook, while users sharing one relayer origin share its cooldown. Router address, `sender` and caller-supplied `hookData` cannot override it. `tx.origin` is never used to authorize an owner operation.

The immutable owner may only pause and unpause individual pools. There is no ownership transfer or renunciation, fee setter, recipient setter, whitelist, backend signer, withdrawal, upgrade, proxy, delegatecall, token minting or arbitrary execution entry point. Losing the owner key can leave a paused pool paused permanently; LP withdrawals and fee claims remain available.

## Operational responsibilities

- The launch operator verifies chain ID, the supplied PoolManager's deployed implementation, constructor arguments, init/runtime sizes and gas for the actual factory transaction, then deploys only `ReedGuardDeployer` and records its emitted hook address. No production RPC rehearsal or broadcast was performed by these offline tests.
- Pool creators and liquidity providers choose their own ERC-20, LP fee, price, ticks and liquidity. There is no pool or liquidity bootstrap action in this launch. Token transfer quirks, token issuer controls and incorrect prices remain their responsibility; the hook does not make fee-on-transfer or rebasing tokens compatible with v4.
- The owner operates `pause(poolId)` and `unpause(poolId)` and protects the immutable owner key. There are no post-launch settings to configure.
- The recipient or any keeper monitors `FeeDeferred` / `claimableFees(poolId)` and submits `claimFees(poolId)` when needed. There is no privileged keeper or keeper reward.
- Integrators use hook-aware v4 quotes, exact PoolIds, caller slippage limits and the displayed cooldown. They must account for ETH-specified partial fills reverting.
- The release process arranges independent adversarial review and the actual Robinhood Chain deployment simulation. Local tests and the included self-review are not an independent audit.
